# YxWoof消费者端 AI 客服项目 README

# 一、产品简述

YxWoof 是面向多商户电商交易场景的消费者端 AI 客服原型。本项目参考了部分开源实现，并围绕“理解诉求—找到正确订单—获取适用依据—明确解释—经消费者确认后办理”建立可追溯的服务闭环。

产品当前只交付消费者会话页，服务对象是在购物前后需要咨询商品与规则、查询订单物流、判断退货资格、准备标准退货申请的消费者。商户工作台、平台管理、真人接管系统和运营看板均不在本期实现范围。

| 核心能力 | 消费者获得的价值 | 控制边界 |
|-|-|-|
| 七类意图理解与字段提取 | 用自然语言说明目标，不必先理解菜单分类 | 诉求不清或多个事项时请消费者选择，不擅自代选 |
| 有据问答与商户范围检索 | 回答附来源，可展开了解适用条件 | 不同商户政策隔离，资料不足时不猜测 |
| 订单、物流、已有申请查询 | 在同一会话中获得明确业务状态 | 仅本人获授权订单，结果标明来源时间 |
| 资格预判、预览、确认提交 | 先了解规则与申请内容，再决定是否办理 | 后端判定资格，预览不写入，确认后唯一提交；受理不等于退款到账 |
| 暂停、恢复、摘要与反馈 | 保留对 AI 的控制权，并能表达未解决问题 | 提供客服联系方式与服务摘要，反馈独立保存 |

**AI-native 的实现方式。**AI 承担语义理解、信息提取和基于来源的解释；身份授权、政策适用性、金额、确认有效性、写入幂等与状态恢复由确定性代码负责。前端采用 React、TypeScript 与响应式卡片交互，后端采用 FastAPI、LangGraph 和 PostgreSQL；知识检索结合 pgvector、中文 BM25、RRF 与重排。模型使用 ECNU的大模型api 接入，凭证只由后端读取。

**演示业务假设。**两个固定合成消费者“小林/小陈”、两个虚构商户“青禾生活/如常好物”和日用收纳商品。两家店分别采用 7 天与 15 天的演示退货时限。仅提交标准退货申请，不执行退款、赔付、改地址或例外裁决；预设客服邮箱 support@yxwoof.example。上述规则不是任何真实平台政策。

**当前完成度。**消费者端 R01–R09 已有可运行实现；800 条参数化场景的测试结果为 785/800（98.125%），正常任务为 385/400（96.25%）。800 条中 560 条走真实模型路径，240 条验证确定性控制或界面行为。

# 二、个人与 AI 协作描述

## （一）具体应用过程

**从业务场景到产品边界。**我先提出以电商客服为对象的产品设计需求，并在讨论中将场景从单一自营商城纠正为多商户电商交易场景。随后进一步限定为 AI 客服改造，不延伸到交易基础设施。AI 辅助拆解场景、用户故事、痛点、目标与非目标，并整理不同方案的价值与复杂度，供我逐步作出范围判断。

**从功能讨论到可实施需求。**我要求依据用户价值、业务价值及实现复杂度划分 P0/P1/P2，使用 EARS 方式描述需求，并明确当前只做消费者端，将商家、平台等其他角色划入 P2。我还要求补齐埋点、过程指标、结果指标、护栏指标、北极星与验收标准。AI 将这些约束串成 PRD、开发计划、接口边界和需求追溯材料；不是直接把参考方案整体搬入项目。

**从文档到远程可运行原型。**在确认尚无现成源码后，项目转为从 0 到 1 的 AI-native 开发。我指定 开发与产物环境，规定 docs/code 路径，命名产品为 YxWoof，并提供统一狗狗客服头像和页面审美方向。在我确认的技术与预算边界内，AI 辅助完成工程搭建、后端领域逻辑、前端卡片与会话交互、模型接入、检索、持久状态、测试和运行说明。

**从能演示到能解释质量。**我没有把“页面能运行”视为完成，而是追问完整验收为何未通过，要求把评测扩大到 800 条，并提供每条对应的数据库数据、完整指标和具体数值。AI 构造合成场景、执行真实模型与确定性测试、保存原始结果并分析失败原因。评测中保留超时、未完成及证据不足，不通过删样本或把模拟结果混入真实 AI 结果来美化数据。

**从真实使用反馈到体验修复。**使用原型时，我发现回答直接显示 Markdown 语法，要求修复；随后继续指出检索证据文档仍未正确渲染，并要求检查同类展示问题。AI 将回答与证据接入统一的安全 Markdown 渲染，保留用户输入和业务字段的原文语义，并补充组件与浏览器测试。这轮协作说明验收不能只覆盖主回复，还要走进来源弹窗、帮助摘要、窄屏和错误状态。

**从正常流程到故障体验。**我继续追问数据库和模型服务故障时的用户体验，明确要求统一提示、独立异常日志、通知接入预留与公开客服联系方式，并要求删去冗长说明。AI 据此补齐异常出口、独立存储与接收协议，在隔离环境中执行故障测试并采集页面截图。

## （二）个人贡献

**问题定义与场景修正。**我的核心贡献是明确产品解决什么问题、服务谁，以及及时纠正“单一商城内部工具”与“多商户场景 AI 客服”之间的差别。这个判断直接影响订单授权、商户政策范围和消费者体验，而不是仅改变产品介绍中的一句话。

**范围与优先级决策。**我推动产品先完成消费者端闭环，将商家端、平台管理和运营能力后置，避免原型被多角色基础设施分散。对于标准退货申请，也明确以“申请受理”为边界，而不是让模型承诺退款结果。

**验收与证据要求。**我提出 EARS 需求写法、指标体系、800 条测评与配套数据库、完整指标数值和验收失败原因分析等要求，促使开发产物不仅包含代码，还具有可追溯的输入、行为、业务状态和结果证据。

**交付组织与体验评审。**我确定服务器、目录、命名、头像与展示方式，并通过实际使用发现两层 Markdown 渲染问题，持续提出具体修正要求。



## （三）关键判断

| 关键判断 | 采用方式 | 价值与代价 |
|-|-|-|
| Ai agent的回复需要结构化，包括意图识别模块，需要维持整条链路严谨可控 | 模型输出结构化意图，授权、规则和确认由后端控制 | 降低误操作风险；需要额外状态机和事务设计 |
| 不能依赖关键词来进行意图识别，例如“我要退货”“还能退吗”“退款到了吗”就必须区别 | 分别归入 application、eligibility、query；直接到账请求归为 unsupported | 相近语言走不同业务路径，避免把询问当成授权 |
| 如果遇到网络延时等情况应该避免多次重复任务的情况 | 当有重复申请时只核实原动作，不自动再创建申请 | 控制重复申请与虚假成功；需要明确的等待与帮助出口 |
| 网页端和手机端都应该做适配，同时ai回复多位专家markdown格式，在前端页面中应该正常渲染 | 回复、来源弹窗与窄屏统一检查； | 提升可读性，并保留脚本与链接安全边界 |

总体协作方式是：我提出目标、约束和质量反馈，AI 把决策转化为可运行实现与可检查证据；每轮根据实际结果继续收敛。AI 提升实现与整理效率，个人判断负责限定正确的问题、可接受的行为和交付口径。

## （十一）异常处理与独立帮助
